# 3D Character Journey — How the Portfolio Animation Works

This doc explains, from the very basics, how the portfolio's 3D character and its
scroll-driven journey are built, how the **movement path** is specified, how
**checkpoints** are established, and how you extend it (or debug why the
character isn't visible).

> It is a **reference**, not a promise that the code is bug-free. The current
> file contents are the source of truth; read the actual files if something
> looks different.

---

## 1. The Big Picture

The portfolio is a normal scrolling HTML page. On top of it sits **one transparent,
full-screen, fixed 3D canvas** that contains **one character** (the `hoornain.glb`
model). As the user scrolls, a `GSAP + ScrollTrigger` timeline continuously moves
that single character, and changes which animation it plays.

Conceptually:

```
Normal page scroll (Hero → Frontend → Backend → AI → HooriGPT → Footer)
   +
Fixed transparent canvas "over" the viewport
   + one character whose position is driven by scroll progress
```

Three separate concerns are deliberately kept independent:

| Concern | Controlled by |
|---|---|
| **POSITION** (where it is) | A scrubbed ScrollTrigger timeline that interpolates between named *waypoints* |
| **FACING** (which way it turns) | A scroll direction state (`forward` / `backward`) |
| **ANIMATION** (which clip plays) | Whether the user is scrolling, and whether a checkpoint is reached |

Keeping these separate is what makes reverse-scrolling work: scroll position
decides *where*, scroll direction decides *which way it faces*, and activity
decides *running vs idle*.

---

## 2. The Very Basics: 3D Coordinate Space

Everything happens in Three.js **world units** inside one canvas.

- The **camera** sits at position `[0, 1.6, 5.2]` and looks at `[0, 1.4, 0]`
  (see `Camera.tsx`). So the "origin" `[0, 0, 0]` is roughly at the center of
  the screen, slightly below eye level.
- **x** = left/right (negative = left), **y** = up/down, **z** = toward/away
  from the camera.
- A `waypoint.position = { x, y, z }` is literally the place the character's
  **outer group** should sit in those world units.
- `rotationY` is a rotation **around the vertical (y) axis** — i.e. which
  horizontal direction the character faces. `0` = facing the camera/viewer.

So "the path" is just a list of `{x, y, z}` positions the character passes
through, one per named checkpoint.

## 3. Files, File by File

The whole system lives under `components/Three/` and is mounted from
`app/page.tsx` via `JourneyExperience`.

### 3.1 `app/page.tsx`

The normal page document flow:

```
LifeUpdateTicker
  ContactRail
  Hero
  FrontendAlter
  BackendAlter
  AIAlter
  HooriGPT
  Ending
  <JourneyExperience />   ← the fixed overlay + controller (last, so it's on top)
```

`JourneyExperience` is rendered **last**, but it is `position: fixed`, so it
doesn't affect layout. The normal browser scroll stays intact — ScrollTrigger
observes it.

### 3.2 `components/Three/JourneyExperience.tsx`

The coordinating wrapper. It creates **one** `useRef<JourneyCharacterHandle>`
and passes the **same ref** into both the scene and the controller:

- `<JourneyScene characterRef={characterRef} />` — renders the canvas + character
- `<JourneyController characterRef={characterRef} />` — drives it via GSAP

Because both share that single ref, the controller always sees the same live
character. This file is `"use client"` (it needs browser APIs/hooks).

### 3.3 `components/Three/JourneyScene.tsx`

The one persistent canvas. It renders a `fixed inset-0 z-30` transparent div
with `pointer-events: none` and `aria-hidden`, so it (a) covers the viewport,
(b) sits above the page sections but below the Contact Rail / ticker (`z-40`),
(c) never blocks clicks, and (d) is invisible to screen readers.

Inside it mounts:

```
<Canvas camera={{ fov: 35, near: 0.1, far: 100, position: [0, 1.6, 5.2] }}>
  <Camera />            ← PerspectiveCamera, looks at [0, 1.4, 0]
  <Lights />            ← ambient + directional + hemisphere light
  <JourneyCharacter ref={...} initialAnimation="waving" />
  <Preload all />       ← preloads GLB data
</Canvas>
```

`initialAnimation="waving"` just sets the very first clip so the page opens with
a waving character.

### 3.4 `components/Three/JourneyCharacter.tsx`

The **one canonical animated character**. It loads `/hoornain.glb` once with
`useGLTF` + `useAnimations`, wraps the model in a `<Center>` + a scaled `<group>`,
and exposes an **imperative handle** (via `forwardRef` + `useImperativeHandle`)
so the controller can command it without React re-renders.

The handle (`JourneyCharacterHandle`) exposes:

| Member | What it does |
|---|---|
| `outer` | The controllable wrapper `Group`. The controller moves/rotates this. |
| `inner` | The animated root group ScrollTrigger-based `useAnimations` is attached to. |
| `names` | The clip names available on the loaded model. |
| `getActions()` | The raw `actions` map (`{idle, running, t-pose, thinking, waving}`). |
| `setAnimation(name, fade?)` | Crossfades to a clip; ignores repeat requests of the current clip. |
| `setPosition(x, y, z)` | Moves `outer` to a world position. |
| `setRotation(x, y, z)` | Rotates `outer`. |
| `setScale(x, y, z)` | Scales `outer`. |

Key constants: `MODEL_URL = "/hoornain.glb"`, `MODEL_SCALE` (the whole-body
scale — tweaking this changes the character's rendered size), and the soft
shadow constants (`SHADOW_RADIUS`, `SHADOW_OPACITY`, `SHADOW_SINK`).

The character renders a `SoftGroundShadow` under its feet so it looks grounded
while moving.

## 4. `components/Three/JourneyController.tsx` — The "Brain"

This is the GSAP + ScrollTrigger orchestrator. It runs on the client, watches the
character ref, and creates all timelines/triggers inside `gsap.context()` +
`gsap.matchMedia()`, so everything is cleaned up automatically (important for
Next.js Fast Refresh — no duplicate triggers).

### 4.1 Flow, very simply

1. When the character handle becomes available (the controller polls for the
   ref), it builds one **GSAP context**.
2. Inside that context it sets up `matchMedia` for desktop / tablet / mobile.
3. For **each leg** in `legs` it:
   - looks up the `from` and `to` waypoints in the current breakpoint's table,
   - resets the character's `outer` group to the `from` position/facing,
   - creates a **scrubbed `ScrollTrigger`** anchored to a DOM section,
   - creates a **timeline** that moves `outer.position` from `from.position` to
     `to.position` (and that's exactly the movement path).
4. ScrollTrigger drives the timeline's progress from the page scroll. Because
   `scrub` is set, the character's position is **continuously** the mapping of
   scroll → progress → interpolated position, both forward and backward.

### 4.2 Tunable constants

| Constant | Value | Meaning |
|---|---|---|
| `SCRUB` | `0.8` | Smoothing lag between the scroll and the animation (0 = instant). |
| `FACE_TURN_DURATION` | `0.45` | How long a direction/checkpoint turn takes (s). |
| `STOP_MS` | `260` | No scroll update for this long ⇒ the character "stopped". |
| `DIRECTION_THRESHOLD_PX` | `10` | Net scroll before a direction flip is accepted (kills flicker). |
| `HERO_REST` | `0.02` | Timeline progress at/below this ⇒ treated as "at Hero". |
| `FRONTEND_REST` | `0.98` | Timeline progress at/above this ⇒ treated as "at Frontend". |

### 4.3 What `applyState` does (animation + facing)

On every scroll update it reads the current timeline progress `p` and:

- `p <= HERO_REST` → play the `from` waypoint's **resting clip** (`waving` at
  Hero) and face the viewer (`restingRotationY`).
- `p >= FRONTEND_REST` → play the `to` waypoint's **resting clip** (`idle` at
  Frontend) and face the viewer.
- `state.scrolling` (still actively scrolling) → play `running` and face the
  travel direction (`travelYaw` forward, `travelYaw + PI` when scrolling back).
- otherwise (stopped mid-travel) → switch to `idle` **in place** (the world
  position is untouched; only the clip changes).

### 4.4 Scroll activity + direction

- `state.scrolling` is set `true` on every `onUpdate`, and a stop-timer is
  (re)started; when it fires (no scroll for `STOP_MS`), `scrolling` becomes
  `false` and the clip relaxes to `idle`.
- Direction is tracked with `lastDir` (`1` = forward/down, `-1` = back/up) and
  only changed after `DIRECTION_THRESHOLD_PX` of accumulated net scroll, so tiny
  reversals can't make the character spin.

## 5. `components/Three/journeyWaypoints.ts` — Where the Path & Checkpoints Live

This is the file that answers "how is the path of movement specified" and "how
are checkpoints established". **Everything is data** — no coordinates are
scattered in the controller.

### 5.1 The three building blocks

```ts
type BreakpointKey = "desktop" | "tablet" | "mobile";

interface Waypoint {
  name: string;                       // e.g. "hero", "frontend"
  position: { x: number; y: number; z: number };  // world position (see §2)
  restingRotationY: number;           // facing when at rest (0 = toward viewer)
  travelYaw: number;                  // facing while RUNNING TOWARD this waypoint
  restingAnimation: JourneyAnimationName; // clip when resting here
  approachAnimation?: JourneyAnimationName; // clip while travelling here (default running)
}

interface JourneyLeg {
  from: string;              // name of start waypoint
  to: string;                // name of end waypoint
  triggerSelector: string;   // CSS selector of the DOM section = scroll anchor
  start: string;             // ScrollTrigger start position ("top bottom")
  end: string;               // ScrollTrigger end position ("top 30%")
}
```

### 5.2 The waypoint table: `JOURNEY_WAYPOINTS`

It is `Record<BreakpointKey, WaypointMap>` — **separate coordinates for desktop,
tablet, and mobile** (because the page layout stacks/reorders across sizes). Each
breakpoint has the same set of named checkpoints:

- `hero` → waving
- `frontend` → idle (beside the laptop)
- `backend` → idle (beside the server)
- `ai` → idle (beside the bot)
- `hoorigpt` → thinking
- `footer` → waving

Example (desktop):

```ts
frontend: {
  name: "frontend",
  position: { x: -2.1, y: -0.3, z: 0.6 },  // left of center, slightly forward
  restingRotationY: 0,                      // faces the viewer when idle
  travelYaw: -0.8,                          // faces the run direction while travelling here
  restingAnimation: "idle",
},
```

### 5.3 How a checkpoint is "established"

A checkpoint is just a named `Waypoint` that the character can rest at. When the
scrubbed timeline for a leg reaches its end (`p >= FRONTEND_REST`), the
controller plays the waypoint's `restingAnimation` and turns the character to
`restingRotationY`. So **"reaching the checkpoint" = the timeline hitting ~1.0
progress**, which happens when the user has scrolled the section to the `end`
position. The static props (laptop/server/bot) are separate DOM canvases — they
stay exactly where they are; the checkpoint is the 3D spot the character walks
to.

### 5.4 How the movement PATH is specified (the key answer)

The **path is the interpolation between two waypoints**, and the **scroll range
is the leg's `start`/`end`**:

```
leg:  hero ──────────────► frontend
       from.position         to.position
       (0, 0, 0)             (-2.1, -0.3, 0.6)

ScrollTrigger (anchor: #frontend, start "top bottom", end "top 30%")
  │ scroll starts → timeline progress 0 → character at hero
  │ scroll advances → timeline progress 0→1 → character interpolates along
  │                    the straight line from hero → frontend
  │ scroll ends   → timeline progress 1 → character at frontend
```

So **one leg = one straight segment** between two waypoints. A multi-checkpoint
journey is just a chain of legs:

```
JOURNEY_LEGS = [
  hero → frontend,   anchor #frontend
  frontend → backend,  anchor #backend
  backend → ai,        anchor #ai
  ai → hoorigpt,       anchor #hoorigpt
  hoorigpt → footer,   anchor #ending
]
```

A "zig-zag" emerges naturally because each checkpoint has a different `x`, so
the straight segments alternate left/right across the screen. If you want a
curved/non-linear path later, you'd add intermediate waypoints (a checkpoint
every bend) or use a `MotionPathPlugin` — but the current system is straight
leg-to-leg interpolation.

### 5.5 `start` / `end` — the scroll window

These are ScrollTrigger position strings relative to the anchor element:

- `"top bottom"` → the leg starts when the section's **top** hits the viewport
  **bottom** (i.e. as the previous section scrolls away).
- `"top 30%"` → the leg ends when the section's **top** reaches 30% down the
  viewport (i.e. the section is well into view).
- `"bottom top"` → ends when the section's bottom reaches the top of the viewport.

Changing these changes how much scrolling a leg spans (faster/slower travel).

## 6. Animation Clips (the GLB)

The `hoornain.glb` contains **exactly these 5 clips** (verified by parsing the
GLB). Do not invent others — there is **no `walking`** clip.

| Clip | Used for |
|---|---|
| `waving` | Hero opening + Footer closing |
| `running` | Travel between checkpoints (the only movement clip) |
| `idle` | Alter checkpoints (rest) |
| `thinking` | HooriGPT |
| `t-pose` | Neutral/bind pose (dev state) |

The character's `setAnimation(name)` crossfades between these with a short
fade (`FADE_DURATION ≈ 0.35s`) and a `currentAction` ref so the same clip is
never restarted on every scroll tick.

## 7. The Static Props (Laptop / Server / Bot)

These are **environmental objects, not the character**. Each has its own small
canvas inside its section (`FrontendScene`, `BackendScene`, `AIScene`) and
renders its `.glb` via the reusable `StaticModel`.

- `StaticModel.tsx` — loads a GLB and applies `position`, `rotation`, `scale`,
  and optional centering (`<Center bottom>`). It does **not** play animations.
- `Laptop.tsx` → `laptop.glb` (scale `0.18`, pos `[1,-1,0]`, rot `[0,-π/1.5,0]`)
- `Server.tsx` → `server.glb` (scale `0.27`, pos `[-1,0,-0.3]`, rot `[0,-π/4,0]`)
- `Bot.tsx` → `bot.glb` (scale `0.13`, pos `[1,-1.2,0]`, rot `[0,π/1.2,0]`,
  `center={false}` because its base is its raw origin)

The character's waypoint positions were chosen so the character stands **beside**
these props at each checkpoint. The props never move — only the character does.
Do not change these transforms (they are the tuned checkpoint landmarks).

`HooriGPTScene.tsx` is now an empty transparent canvas (Lights only) — the
duplicated character was removed; the journey character reaches that region via
the persistent canvas.

## 8. How to Add a New Checkpoint / Leg (step by step)

1. **Pick a name**, e.g. `"projects"`.
2. In `journeyWaypoints.ts`, add a `projects` entry to **each breakpoint's**
   table (`desktop`, `tablet`, `mobile`) with:
   - `position` (world coords it should rest at),
   - `restingRotationY` (usually `0` = face viewer),
   - `travelYaw` (facing while running toward it),
   - `restingAnimation` (e.g. `"idle"`).
3. Add a leg to `JOURNEY_LEGS`, e.g.
   `{ from: "ai", to: "projects", triggerSelector: "#projects", start: "top bottom", end: "top 30%" }`.
   Make sure the DOM section actually has `id="projects"`.
4. That's it — the controller iterates `legs` generically, so the new segment
   is picked up automatically with position, facing, and animation all handled.

**Tuning** lives entirely in the waypoint numbers and the controller constants
table (§4.2). No component changes needed for new checkpoints.

## 9. Responsive Waypoints

`JOURNEY_WAYPOINTS` has a full coordinate set per breakpoint because the page
layout changes: on desktop the stages are side columns, on mobile everything
stacks and the character should mostly travel vertically with restrained X.

- `desktop` → full horizontal/diagonal reach.
- `tablet` → reduced reach.
- `mobile` → mostly vertical, small X.

The controller chooses the right table at runtime via `window.matchMedia`
(breakpoints: `≥1024`, `768–1023`, `≤767`) inside `gsap.matchMedia()`. When the
viewport crosses a breakpoint, GSAP rebuilds the matching timelines and the
character snaps to the new `from` waypoint (the page reload/refresh behavior).

## 10. Troubleshooting — Why the Character Might Be Invisible

If the character isn't visible at all, work through these in order:

1. **Is the dev server actually running the latest code?** Restart `npm run dev`
   and hard-refresh. A stale Fast Refresh state (especially after many edits)
   can leave the canvas unmounted. Check the browser console for a red error.
2. **Is there a runtime error in `JourneyController`?** Because
   `JourneyExperience` renders both the canvas and the controller together, an
   exception inside the controller's `matchMedia`/`ScrollTrigger` setup can
   unmount the **whole subtree — including the canvas** (so no character shows).
   Open DevTools console; a thrown error here is the #1 suspect.
3. **Is the `z-index` correct?** The canvas is `fixed inset-0 z-30` with
   `pointer-events: none`. If a section or overlay uses a higher z-index, the
   canvas sits underneath and the character is hidden behind page content. The
   Contact Rail / ticker are `z-40` (intended above); section content should be
   ≤ `z-10`.
4. **Is the character's `outer` position inside the camera frustum?** Waypoint
   coords like `x: 1.9` with camera at `[0,1.6,5.2]` and fov 35 should be
   visible, but if a coordinate is far outside (large `x`/`z`), the character is
   off-screen. Start with `hero` at `[0,0,0]` to confirm it appears dead-center.
5. **Is the ref wired?** `JourneyController` only builds triggers once
   `characterRef.current?.outer` exists (it polls every 200ms). If the handle
   never populates, no timeline runs. The `initialAnimation="waving"` in
   `JourneyScene` still plays, so the character should at least wave in place.
6. **Scale / camera**: if `MODEL_SCALE` is tiny or the camera is far, the
   character is too small to see. Confirm `MODEL_SCALE` (~99) and the camera
   `[0,1.6,5.2]` fov 35 are intact.
